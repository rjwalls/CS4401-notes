Ghidra is the static-analysis tool we will use when a challenge gives us a
binary but withholds its source. Complete this mini-lab after Stack 2 and before
Warp Drive. Use the source-provided Stack 2 lecture binary for practice; do not
turn the lab into a walkthrough of the companion challenge.

## Import and analyze the binary

1. Create or open a non-shared project.
2. Import the downloaded `stack2-64` ELF file.
3. Open it in CodeBrowser and accept the default analysis options.
4. Confirm that Ghidra identifies x86-64 little-endian code and discovers the
   program's functions and symbols.

The Symbol Tree and Functions list help you navigate known functions. The
Defined Strings window is often a faster entry point: find a distinctive output
message, inspect its references, and follow the cross-reference into the code
that prints it.

## Decompiler versus disassembly

The Listing shows the instructions the processor executes. The Decompiler
offers a C-like interpretation of those instructions. The decompiler is useful,
but it is not recovered source and it can guess types, boundaries, or control
flow incorrectly. When a detail determines your exploit, confirm it in the
Listing.

For each important function in Stack 2:

1. Read the decompiled control flow.
2. Find the corresponding indirect call in the Listing.
3. Identify where the input buffer and function pointer live relative to the
   stack-frame base.
4. Compare that conclusion with GDB/GEF while the process is running.

## Rename and retype what you learn

Ghidra starts with names such as `local_58` and types that may be vague or
wrong. Rename variables and functions as their roles become clear. Retype the
input as a byte array and the target as a function pointer. Add short comments
for facts that matter to the exploit, such as the input call, overwrite offset,
and indirect call site.

This is not cosmetic. A useful analysis database records your current model so
you can test and revise it instead of repeatedly rediscovering the same facts.

## Strings and cross-references

Find the strings printed by the normal diagnostic path and the recalibration
path. Use their cross-references to locate both functions. Then answer:

- Which function receives attacker-controlled input?
- What object is adjacent to that input?
- Where is the indirect call that consumes the corrupted pointer?
- Which function prints the flag?

## PIE offsets

Ghidra normally shows addresses relative to the ELF image. For a non-PIE
executable, those code addresses are stable. For a PIE executable, treat a
symbol's Ghidra address as an offset within the executable:

```text
runtime address = runtime PIE base + ELF symbol offset
```

If the program leaks one known function at runtime:

```text
PIE base = leaked runtime address - leaked function's ELF offset
```

You can then add the target function's ELF offset. Differences between symbols
inside the same executable remain stable even when ASLR changes the base.

## Mini-lab deliverable

On the Stack 2 lecture binary, record renamed functions and variables, the
buffer-to-function-pointer offset, the relevant input and indirect-call
instructions, and whether the binary is PIE. Explain how those observations
match the source and your working exploit. Warp Drive will ask you to repeat
that analysis without source.
